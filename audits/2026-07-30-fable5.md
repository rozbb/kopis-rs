# kopis-rs Security & Correctness Audit

**Date:** 2026-07-30
**Scope:** Entire crate at commit `5bcc4e5` — core protocol (`kem.rs`, `pke.rs`, `sample.rs`, `ser.rs`, `impls.rs`), serial arithmetic (`arithmetic/`), AVX2 and NEON backends + shared CRT layer (`backend/`), `build.rs`, tests/KATs, CI, docs, and dependencies. Checked against the spec at `lean/kopis-spec.md`. The Lean proofs themselves were out of scope (known to be out of sync).
**Method:** Manual line-by-line review of the protocol layer, plus four parallel deep reviews (serial arithmetic, AVX2+CRT, NEON, tests/API/deps) backed by numeric verification: exhaustive checks of the modular-reduction routines over their full input domains, independent recomputation of all twiddle/CRT constants, certified interval propagation of the lazy-reduction bounds through every butterfly layer, and bit-exact end-to-end models of both vector pipelines compared against exact integer negacyclic products. `cargo test --release` passes (33 tests) on this AVX2 host.

**Bottom line:** No spec mismatch was found anywhere in the shipped code paths: the FO transform, rounding constants, domain separators, CBD, serialization bit-order, and all sizes match the spec, and the NTT arithmetic in all three backends was verified exact within its bounds. The serious findings are *deployment/assurance* issues: an unsound NEON build-gating decision on softfloat AArch64 targets, KAT provenance that cannot be independently verified, and CI that never exercises the NEON backend. Below that are hardening and documentation-accuracy issues — several load-bearing safety comments are wrong even though the code they describe is right.

---

## High

### H1. NEON backend is enabled for *all* AArch64 targets, which is unsound on softfloat targets

**Where:** `build.rs:111-117` (autodetect), `build.rs:95-106` (forced-`neon` override), `src/backend/neon/cpu.rs:13-15`

`build.rs` sets `kopis_neon` whenever `CARGO_CFG_TARGET_ARCH == "aarch64"`, and `neon::available()` returns `true` unconditionally, on the theory that NEON is baseline on AArch64. But rustc supports softfloat AArch64 targets (e.g. `aarch64-unknown-none-softfloat`) where enabling the `neon` target feature is ABI-incompatible. Verified empirically: `cargo build --target aarch64-unknown-none-softfloat` currently *succeeds* and emits, for every `#[target_feature(enable = "neon")]` function, rustc's warning that this is "unsound due to ABI issues" and will become a hard error (rust-lang/rust#134375).

**Impact:** A bare-metal/kernel AArch64 consumer — a real audience for a `no_std` crate whose CI deliberately exercises a bare-metal thumbv7em build — gets undefined behavior today (NEON code called across a softfloat ABI boundary; SIMD state may not even be enabled at that exception level) and a hard build failure on a future rustc. The forced-`neon` override claims to "verify it is actually available" but only checks the architecture.

**Recommendation:** Gate `kopis_neon` on `CARGO_CFG_TARGET_FEATURE` containing `neon` (or reject `CARGO_CFG_TARGET_ABI == "softfloat"`), in both the autodetect and override paths.

### H2. KAT provenance is unverifiable, so the external-validation story is weaker than it appears

**Where:** `tests/pqm4_kat.rs:1-2`, `tests/pqm4_test_vectors-kopis*-{speed,stack}.txt`, `tests/ref_kat.rs`, `lean/SpecTests/Kopis/TestVectors.lean:7`

The pqm4 KAT header claims the vectors are "distributed with the pqm4 implementation of Kopis", but no pqm4 URL, commit hash, or generator script is recorded anywhere; git history says only "Commit PQM4 test vectors". The repo's own Lean test file states "Kopis does not yet ship with published known-answer test (KAT) vectors" (that comment is stale — the same file now runs them — but it contradicts the provenance claim). The file format is custom (6-line `keyseed/.../ss` groups matching this crate's unusual seed-only secret-key design), not standard pqm4/NIST `.rsp` output. Additionally, the "speed" and "stack" vector files are **byte-identical** for all three parameter sets (`cmp` confirms), so the test's claim that two pqm4 implementations "must agree with each other" is vacuous — the same file is run twice.

**Impact:** If these vectors were generated by this codebase (or a common ancestor), the pqm4 KATs are circular self-KATs: they would pass even if the implementation had diverged from the intended spec at generation time. Since the Lean proofs are currently out of sync, KATs are the *only* active defense against spec divergence, and their independence cannot be established from the repo. Mitigation that does exist: the `ref_kat` jsonl vectors are byte-identical to the ones consumed by the Lean spec runner (`make test-kopis-spec`), giving genuine cross-validation against the Lean spec — but that runner is not in CI (see M4) and the jsonl's own origin is also undocumented.

**Recommendation:** Record the exact pqm4 commit and generation command for the vectors (or regenerate from a pinned upstream and check in the provenance); replace one of the duplicate speed/stack files with a genuinely independently-generated set or delete the duplicate; add the Lean spec-KAT runner to CI.

### H3. CI never compiles or tests the NEON backend

**Where:** `.github/workflows/ci.yml:59-72`

All CI jobs run on `ubuntu-latest` (x86). Every NEON test (`neon_matches_serial` in `src/arithmetic/ntt.rs:625`, the CBD `matches_serial` in `src/backend/neon/sample.rs:69`, `transpose8_permutes_as_documented` in `src/backend/neon/ntt.rs:792`) is behind `#[cfg(kopis_neon)]`, which is only set on aarch64, so CI reports green while exercising zero NEON code. There is not even a `cargo check --target aarch64-unknown-linux-gnu` cross-build; a NEON *compile error* would ship undetected.

**Impact:** Any regression in `src/backend/neon/` — which contains most of the crate's `unsafe` — merges with green CI and is first discovered by a user on Apple/Graviton hardware.

**Recommendation:** Add an aarch64 job (GitHub now offers arm64 runners; or QEMU via `cross`) running the full test suite, plus at minimum a cross-`cargo check` for `aarch64-unknown-linux-gnu` and `aarch64-unknown-none-softfloat` (the latter to catch H1).

## Medium

### M1. Forced-AVX2 builds can silently produce binaries that execute AVX2 unguarded on CPUs without it

**Where:** `build.rs:185-198` (`avx2_is_available`), `src/backend/avx2/cpu.rs:27-31`

With `--cfg kopis_backend="avx2"` and *no* `-C target-feature=+avx2`, the build script accepts the configuration if the build is not a cross-compile and the **build host's** CPU has AVX2. `available()` then constant-folds to `true` (`kopis_avx2_assume`), so the produced binary contains no CPUID check and no fallback. Build on an AVX2 CI machine, deploy to an older x86-64 VM → unguarded AVX2 execution (SIGILL at best; UB by Rust's target-feature rules). The mode is documented as "no runtime check", but the host-CPU auto-pass makes the hazard easy to hit without ever writing `+avx2`.

**Recommendation:** Make the forced mode require `avx2` in the target feature set, and treat "host CPU has it" as insufficient (or demote it to enabling the *runtime-checked* backend).

### M2. The two vector backends' Barrett-reduction schedules diverge, and the shared correctness documentation is wrong for AVX2

**Where:** `src/backend/crt.rs:46-48`, `src/backend/avx2/ntt.rs:75-77,488-490`, `src/backend/neon/ntt.rs:29-31`

`crt.rs` documents the forward schedule as "a Barrett pass after levels 3 and 6" and claims both backends follow it; `neon/ntt.rs` claims its numbering "matches AVX2's… so the growth bounds carry over unchanged". Neither is true: NEON reduces after levels 3, 6, 8; AVX2 reduces after levels 3 and **7** (its inline comment "Three more levels of growth" miscounts a four-level run). Under the documented +0.75·q-per-level budget, AVX2's 4-level run computes to 3.5·q — *above* the 3.047·q i16 limit, i.e. the written argument predicts an overflow that doesn't happen. Certified interval propagation with the actual per-butterfly ζ magnitudes shows the code is safe: worst lane ≈ 30,680 of 32,767 for AVX2 (≈6.4% headroom) and 23,626 for NEON. But AVX2's safety rests on table-specific ζ magnitudes at levels 4–7, a fact stated nowhere.

**Impact:** No bug in shipped code. The risk is maintenance: anyone regenerating the ψ tables or "harmonizing" the schedules while trusting the written argument could introduce a real i16 overflow that produces wrong ciphertexts only for rare inputs — exactly the kind of bug randomized tests miss.

**Recommendation:** Either move AVX2's second Barrett pass to after its len=4 loop so the documented schedule is true, or fix the three doc sites to describe the real 3+4 schedule and record the sharper, table-dependent bound.

### M3. Intermediate secrets are systematically left unzeroized on the stack

**Where:** `src/sample.rs:107` (`backing_buf`, the raw XOF bytes that determine the secret), `src/pke.rs:147` (`secret_seed`), `src/pke.rs:161` (`vec_s`, coefficient-domain secret), `src/pke.rs:234-235` (`vec_sprime`/`sprime_ntt`, ephemeral encryption secret), `src/kem.rs:148,151-152,164` (`randomness`, `k`, `rprime`, and the reconstructed ciphertext in `decap`), `src/kem.rs:121` (`r` in encap), plus XOF/hasher states throughout, and the scratch buffers inside the backends' NTT/sampler paths.

The crate visibly commits to zeroization (`ZeroizeOnDrop` on all key types, `SharedSecret` zeroized, `seed`/`randomness` locals explicitly zeroized in `generate`/`encapsulate`) — but every *intermediate* secret listed above is dropped without wiping, so the protection is inconsistent: the long-term key is wiped while the CBD bytes that generated it, the coefficient-form secret vector, and decap's decrypted message linger on the stack.

**Impact:** Hardening only (matters for cold-boot/memory-disclosure/core-dump scenarios); stack zeroization is inherently best-effort. But the current state gives a false sense of coverage.

**Recommendation:** Add `.zeroize()` calls (or `Zeroizing` wrappers) to the listed locals; state the intended zeroization policy in the crate docs, including its limits (register/stack copies, hasher state). Related: `RingElem`/`NttElem` are `Copy`, which invites silent secret copies that no drop-based scheme can wipe — worth a comment, or removing `Copy` from `NttElem` where practical.

### M4. CI does not verify the Lean artifacts it advertises

**Where:** `.github/workflows/ci.yml` (whole file), `extract_rust_to_lean.sh`

CI runs cargo test/fmt/clippy and a no-std build only. Nothing checks that `lean/ExtractedRust.lean` is current with the Rust, or runs `make test-kopis-spec` (the Lean spec-KAT runner that is the independence anchor for the ref KATs, per H2). The current known drift (proofs out of sync) is exactly the failure mode an extraction-currency check would have caught.

**Recommendation:** Add a CI job that re-runs the extraction and fails on diff, and one that runs the Lean spec KAT runner. (The extract script currently hardcodes `/home/dev/aeneas/...` paths — it needs to be made portable first.)

### M5. All hashing rests on `turboshake`, a niche single-maintainer crate with a non-exact pin

**Where:** `Cargo.toml:12` (`turboshake = "0.7"`)

Every secret-deriving operation in the crate flows through `turboshake 0.7.x`. It does delegate the permutation to the widely-reviewed RustCrypto `keccak` crate, which limits exposure to the sponge/XOF layer, but it is not audited on the level of RustCrypto `sha3`, and the semver-range pin means any consumer not using this repo's `Cargo.lock` picks up a hypothetical compromised 0.7.x patch release automatically.

**Recommendation:** For a production KEM: pin exactly, vendor, or document a review of the crate (its XOF layer is small); alternatively implement TurboSHAKE over `keccak` directly.

## Low

### L1. Memory-safety preconditions carried by *safe* `#[target_feature]` functions
`src/backend/avx2/ser.rs:82`, `src/backend/avx2/sample.rs:63`, `src/backend/neon/ser.rs:80`, `src/backend/neon/sample.rs:39`. These functions have "# Safety"-style length preconditions whose violation is an out-of-bounds SIMD read (e.g. a 16-byte head-group load past a short buffer), but they are declared as safe fns — so any *other* target-feature function in the crate can call them without `unsafe`. All current call sites uphold the contracts (asserted at `ring_arith.rs:42,47`, by construction in `sample.rs`). Mark them `unsafe fn`, or add a one-line length assert (cost-free next to the SIMD work).

### L2. AVX2 `cbd` contract admits `MU = 12`, for which it silently returns wrong coefficients
`src/backend/avx2/sample.rs:61,31-42`. The stated domain is "even and in `2..=13`", but `popcount_small` is only valid for fields below 32 (5 bits); at MU=12 bit 5 of each 6-bit half is dropped. Unreachable with today's parameter sets (μ ∈ {6,8,10}), but a future parameter set would sample a wrong distribution with no assert or test firing. Tighten the contract to `MU ≤ 10` and add a `const`-assert.

### L3. Load-bearing arithmetic comments in the serial layer are wrong (code is right)
- `src/arithmetic/ntt.rs:109`: `barrett_reduce`'s documented output bound "|r| ≤ p/2 + 1" is false — exhaustive check gives p/2 + **41** worst-case over i32 (p/2 + 15 over the range it actually sees). The wrong "+1" propagates into the overflow arguments at `ntt.rs:170,203,289`. The whole chain still holds with the true bound (verified: 16·(p/2+41) < 2³¹; 4·(p/2+41)² < 2³¹·p), but anyone tightening margins while trusting "+1" could be misled.
- `src/pke.rs:173`: "b's coefficients are 10-bit after the rounding shift" is false — b carries mod-2¹⁶ garbage in bits 10–12. This is safe for three subtle reasons (the `from_uniform` precondition is < 2¹³; the exactness bound already assumes 8191-magnitude operands; the garbage contributes only multiples of 2¹⁰, which ciphertext serialization masks off — so keygen-cached and `from_bytes` public keys still encrypt bit-identically, which the FO re-encryption compare depends on). The comment should state the real invariant.

### L4. Release builds rely on `debug_assert!` for two arithmetic-safety bounds
`src/arithmetic/ntt.rs:371,390`: the inner-dimension bound (≤ MAX_L = 4) that keeps the pointwise accumulator inside both the serial exactness window and the AVX2 i32 accumulator range is debug-only; a future caller with a larger dimension would silently compute wrong results. `src/arithmetic/matrix_arith.rs:108`: `Matrix::deserialize_10` uses `debug_assert_eq!` for its length check where sibling routines use hard `assert!`. Both are unreachable today; promote to `assert!`/`const`-checks for defense in depth.

### L5. `tests/ref_kat.rs` can pass vacuously
`tests/ref_kat.rs:93-101`: no non-emptiness assertion (unlike `pqm4_kat.rs:137`), and every `malformed: true` vector is skipped — a truncated or all-malformed jsonl passes with zero assertions executed. Of 24 vectors per level, the 10 malformed ones contribute nothing (they describe wrong-length inputs the fixed-array API cannot express). Assert a minimum count of *executed* vectors.

### L6. `seed()` returns the complete long-term secret without a sensitivity warning
`src/impls.rs:65-68`: the doc says only "Returns the seed that produced this secret key". This 32-byte value *is* the secret key, and bytes copied out of it escape zeroize-on-drop. One doc sentence ("this is the secret key; handle/erase accordingly") fixes it. Related (info): `SharedSecret` offers no constant-time equality (`subtle::ConstantTimeEq` impl), so callers who need to compare are pushed toward the non-CT `as_bytes()` comparison the README itself warns about.

### L7. "Bit-identical, checked by tests in each module" overstates test placement, and hardware-gated tests skip silently
README + `src/backend/avx2/mod.rs:3-5`: the `avx2/ser.rs` and `neon/ser.rs` modules have no test modules; bit-identity is covered only indirectly (via `ring_arith` dispatch tests and KATs — coverage that is adequate but not where the docs say). Moreover every backend test begins `if !available() { return; }`, so on hardware without the feature they pass silently rather than reporting as skipped. Fix the claim or add per-module direct sweeps; consider printing/streamlining skip visibility.

### L8. README-only pushes skip CI, but the README is a compiled doctest
`.github/workflows/ci.yml:6,9` (`paths-ignore: README.md`) vs `lib.rs:13` (`#![doc = include_str!("../README.md")]`): a README commit that breaks the example lands with no CI run and fails on the next unrelated push. Drop the ignore.

### L9. Secret-holding internal types derive `Debug`, `PartialEq`, and `Copy`
`src/arithmetic/ring_arith.rs:15`, `matrix_arith.rs:12`, `ntt.rs:206`: `RingElem`/`Matrix`/`NttElem` (which carry the secret vector) derive `Debug` (accidental logging prints secrets), non-constant-time `PartialEq` (currently used only by tests), and `Copy` (see M3). All crate-internal, so exposure requires an internal mistake — but for a bulletproof crate, deriving these only under `#[cfg(test)]` is cheap.

## Informational

- **`kopis_neon_assume` is dead**: emitted by `build.rs:105` but read nowhere (its AVX2 twin is consulted in `avx2/cpu.rs`); falsely suggests NEON has a runtime-detection distinction.
- **`barrett_reduce` interior wrapping** (`src/arithmetic/ntt.rs:93-100`): `q.wrapping_mul(P)` genuinely wraps i32 for |x| ≳ 43p; the double wrap cancels mod 2³² and the result is correct for *every* i32 (exhaustively verified), but the "never actually wraps" comment is only true for pipeline-range inputs.
- **`neon_matches_serial`** (`src/arithmetic/ntt.rs:560-618`) accumulates the same product ℓ times rather than ℓ distinct products, so cross-operand accumulator mixing is only exercised end-to-end.
- **Constant-time caveat**: the CT argument everywhere assumes fixed-latency wide multipliers — true on mainstream x86-64/AArch64, not guaranteed on some small in-order cores the portable backend could target (e.g. certain Cortex-M with early-terminating multipliers). Worth one sentence in the docs given the no-std/embedded audience.
- **Aligned loads on `repr(Rust)` struct fields** (`src/backend/avx2/ser.rs:33-38,86-91`): `Plan` is `repr(align(32))` but not `repr(C)`; the assumed field offsets hold under every real rustc layout but are not formally guaranteed. `repr(C)` or `loadu` (free on AVX2) closes it.
- **Stale comment**: `lean/SpecTests/Kopis/TestVectors.lean:7,18` still says no KATs exist while the same file runs them.
- **`license = "MIT/Apache-2.0"`** (Cargo.toml) is deprecated SPDX syntax; use `"MIT OR Apache-2.0"`.
- **`cargo hack --each-feature`** in CI is vacuous — the crate declares no features.
- **Cosmetics**: typo "aboev" (`ring_arith.rs:65`); `ZETAS[0]` never read (standard for this table layout, and its value is correct anyway); `bench.sh` unquoted `$@`; untracked `graviola/`/`libcrux/` reference checkouts in the repo root (unused by the build — consider `.gitignore`); `extract_rust_to_lean.sh` hardcodes `/home/dev/aeneas/...`.

## What was checked and found sound

For an audit, the absence-of-findings list matters as much as the findings:

- **Spec conformance (core protocol):** FO transform structure, `ExpandDecapKey` (including the `sk || ℓ` domain-separating byte), rounding constants h₁/h₂ at every use, all six domain separators, CBD bit-ordering, GenMat/GenSecret XOF invocations, serialization bit-order (LSB-first), and all PK/CT sizes (672/736, 992/1088, 1312/1472) match `lean/kopis-spec.md` exactly. The spec's constant-time MUST for decap is honored via `subtle::ct_eq` + `conditional_select`, with the rejection value and `k` both always computed.
- **Serial NTT exactness (the core correctness question):** p = 50,330,113 verified prime, ≡ 1 (mod 512); all 256 twiddles independently recomputed and matched; worst-case accumulated coefficient 25,162,752 vs capacity 25,165,056 — the bound is attainable (an existing test hits it exactly) and holds even for the dirty-b case (L3) and malicious ciphertexts (deserialization masks every coefficient to 10 bits). `mont_reduce`/`barrett_reduce`/`to_wrapping_u16` verified exhaustively or over their full contract domains; both transforms proven i32-overflow-free; the mod-2¹⁶ wrapping-congruence argument traced through every shift (which bits each downstream consumer keeps) and found airtight.
- **AVX2/NEON backends:** all constants of both 16-bit primes (primality, 512th roots, all 512+512 twiddles, Montgomery/Barrett/Garner/scale constants) independently recomputed and correct; lane-exact end-to-end models of both pipelines match the exact integer negacyclic product on random + adversarial extremal inputs for all parameter sets; the NEON `vqdmulh`/`vhsub` Montgomery trick verified exhaustively over all 2¹⁶ inputs × every multiplier with zero saturations; CRT recombination windows verified to cover the worst case; every unsafe block's pointer arithmetic, lane counts, and type reinterpretations re-derived and found in-bounds; the CPUID path checks OSXSAVE and XGETBV (XCR0 XMM+YMM) before believing the AVX2 bit — the classic "OS doesn't save YMM" bug is *not* present.
- **Side channels:** no secret-dependent branches, secret-indexed memory addresses, or variable-time operations on secrets in any backend (serial, AVX2, NEON), the sampler, or serialization; the only lookups touching secret data are register-resident `vpshufb`/`vqtbl1q` with public indices. Dispatch branches only on public CPU features.
- **Public API:** no reachable panics (all entry points take fixed-size arrays); key types are `ZeroizeOnDrop` with only public fields skipped; `SharedSecret` is not `Debug`/`Clone`/`PartialEq`; auto `Send`/`Sync` are sound; README example compiles and runs as a doctest.
- **Dependencies:** four runtime deps (`rand_core`, `turboshake`, `subtle`, `zeroize`), all registry-sourced and checksummed, no git/path deps, dev-deps properly confined; `build.rs` does nothing beyond cfg selection.
- **Implicit rejection is genuinely tested:** the ref KATs include 6 mauled-ciphertext vectors per level asserting the exact pseudorandom rejection output, and a unit test models an FO adversary.
