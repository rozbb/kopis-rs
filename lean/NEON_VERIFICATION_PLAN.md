## 1. Three things that make this cheaper than AVX2 was

**(a) The CPU probe is gone from the trust base.** On AArch64 NEON is baseline, so
`cpu::available()` is `cfg!(target_arch = "aarch64")` — a compile-time `true`. It is *not*
extracted opaquely, and comes out as

```lean
def backend.neon.cpu.available : Result Bool := do
  ok true
```

So the dispatch points do not need proving on both branches; they reduce to the NEON branch. No
`available_ok`, and no `gen_neon_bridge.py` counterpart to AVX2's `gen_avx2_bridge.py`, which
exists only to patch the four `cpu::available` sites in the twins. `rangeInclusive_contains_ok`
is still needed, for the same `(1..=13).contains(&bits)` width guard.

**(b) The permutes are simpler.** AArch64 vectors are 128 bits and `TRN1`/`TRN2` act across the
whole register, so there is no equivalent of AVX2's "acts within each 128-bit half" quantifier —
the classic AVX2 error simply cannot be made here. `transpose8` is three `TRN` stages at widths
16, 32 and 64 against `transpose16`'s two-half `unpack` network plus a `vperm2i128` pass, and
the narrowing (`xtn`/`shrn`) leaves lanes in order where `vpackusdw` interleaves them and needs
a `vpermq` to repair. Expect `Kopis/Neon/Transpose.lean` to be materially smaller than
`Kopis/Avx2/Transpose.lean` + `TransposeSpec.lean` (674 lines).

**(c) Much of the AVX2 proof is about the *scheme*, not the instruction set.** `Kopis/Avx2/`'s
`Crt.lean`, `NttAlgebra.lean`, `NttZeta.lean`, `Tables.lean` and `MulT.lean` are about the
two-prime CRT transform that both backends share (`src/backend/crt.rs`). Read them before
writing anything: what is genuinely new here is the lane arrangement, not the mathematics.

## 3. The measurement

Comparing the serial and NEON extractions declaration by declaration:

```
declarations: serial=348  neon=516  shared-name=348
  only in neon : 168   (ntt 71, intrinsics 47, keccak 17, sample 15, ser 14, cpu 1, core 3)
  reaching into the NEON backend from a shared name : 8
```

Those eight are exactly the runtime-dispatch points, and they are the work list for the
twin stack:

```
arithmetic.ntt.NttElem.from_uniform          arithmetic.ring_arith.RingElem.deserialize
arithmetic.ntt.NttElem.from_secret           sample.gen_matrix_from_seed
arithmetic.ntt.pointwise_mul_acc             sample.gen_secret_from_seed
arithmetic.ntt.reduce_invntt_to_ring_elem    sample.gen_secret_from_seed_loop
```

Two more than AVX2's six, and the extra two are the batched XOF: `gen_matrix_from_seed` and
`gen_secret_from_seed` divert to `backend::neon::sample`, which drives the two-way TurboSHAKE.
AVX2 has the same shape, but its `sample.gen_matrix_from_seed` was already counted in its six.
`gen_secret_from_seed_loop` is the odd one — NEON keeps a *second* dispatch inside the portable
loop, for the `MU` values whose fields straddle byte boundaries, which AVX2 has no counterpart
for because its four-lane batch has already returned by then.

## 4. Operating notes

Everything under "Operating notes" in `AVX2_VERIFICATION_PLAN.md` applies. Two additions.

**Extraction is a cross-compile.** `charon cargo … -- --target aarch64-unknown-linux-gnu`, with
`RUSTFLAGS='--cfg kopis_backend="neon" -C target-feature=+sha3'`. The sysroot charon builds
carries full MIR for that target, so nothing special is needed beyond
`rustup target add aarch64-unknown-linux-gnu`. (This stopped being a *difference* from AVX2 on
2026-08-07: the AVX2 extraction now names `x86_64-unknown-linux-gnu` explicitly too, so that
neither vector extraction depends on what the host happens to be. It remains an addition over
the AVX2 plan as written.) The `+sha3` is not optional — without it
`build.rs` drops `backend::neon::keccak` and the batched samplers, and the extraction silently
covers a *different, smaller* backend. **A NEON build without FEAT_SHA3 is therefore not covered
by any of this**, and closing that would mean a fourth extraction.

**Isolate aeneas failures with `--start-from`.** A whole-crate aeneas run takes about two
minutes; `charon cargo … --start-from 'kopis::backend::neon::ntt::invntt_block'` plus aeneas on
the result takes eleven seconds, and the span aeneas reports is accurate. This turned a
multi-hour bisect into a ten-minute one and is the first thing to reach for.

**New aeneas traps, found here.** These are in addition to the three in the AVX2 plan.

4. **`let (x, y) = if COND then … else …` at statement level fails** when the bound tuple is then
   consumed by a following loop — "Internal error, please file an issue" from
   `simplify_let_branching` (`pure/PureMicroPassesGeneral.ml:1312`). The *same* shape at the top
   of a loop body translates fine, so it is not the `if` alone. Moving the branch into its own
   function body, as the tail expression, fixes it: that is what the six `fwd4`/`inv1`/… table
   accessors in `neon/ntt.rs` are for. Note the accessors must return the loaded pair **by
   value** — returning the `&'static Tbl<N>` instead runs straight into trap 1.
5. **A leaf module name that shadows a crate-root module breaks name resolution in the output.**
   `backend::neon::sample::secret` calls both its own `cbd` and the portable `crate::sample::cbd`;
   aeneas emits the latter as `sample.cbd`, and Lean, elaborating a declaration named
   `backend.neon.sample.…`, resolves that against the enclosing namespaces first and finds
   `backend.neon.sample.cbd`. The extraction then fails to typecheck on an arity mismatch. The
   fix was renaming the NEON one to `cbd_lanes`. AVX2 does not hit this because its `secret`
   never calls the portable sampler. **Anything new in `backend::neon::*` that calls a
   same-named crate-root item will hit it.**

## 5. The phases

Same spine as AVX2's, with the differences above folded in.

### Phase A — get the intrinsic model tested. *Done; A2 was blocked on hardware until 2026-08-07.*

Two halves, and only one could be done in the original environment.

1. **`Kopis/Neon/Model.lean`** — a computable `BitVec` model per operation, and a theorem per
   operation deriving it from the axiom (`∃ c, f a b = ok c ∧ bits c = Model.f (bits a) (bits b)`).
   This is pure Lean and can be written now. Follow `Kopis/Avx2/Model.lean` exactly.
2. **The vectors.** Someone with an Apple silicon or other FEAT_SHA3 AArch64 machine runs

   ```sh
   RUSTFLAGS='-C target-feature=+sha3' KOPIS_REGEN_VECTORS=1 \
     cargo test --lib neon::intrinsics_vectors
   ```

   and commits `tests/neon_intrinsics_vectors.jsonl`. **The Lean side of this is now written**
   — `SpecTests/Neon/Run.lean`, `lean_exe neonTests`, `make test-neon-model` — so on that host
   the whole of A2 is those two commands. Done 2026-08-07; see the phase A2 entry at the end,
   which is also where the environment setup a fresh AArch64 host needs is recorded.

Read the module docs of `intrinsics_vectors.rs` before touching the generators: three operations
(`tbl1_u8`, `ushl_u16`/`ushl_u32`, `sqdmulh_s16`) are *vacuous* on uniformly random input and
have structured generators for that reason. The AVX2 side learned this from a corrupted-model
check that passed anyway.

**Acceptance:** `make prove-kopis` green; the runner passes on ≥ 1000 vectors per operation; and
a deliberately corrupted model makes it fail — record that negative check, do not commit the
corruption. *All three met on 2026-08-07.*

### Phase B — lane algebra

`Kopis/Avx2/Lanes.lean` is 241 lines of which almost everything (`concatLanes`,
`laneOf_concatLanes`, `eq_of_laneOf_eq`, `laneOf_split`, `laneOf_laneOf`, `laneOf_and`) is about
`BitVec` and does not mention an extracted constant. Only the four `Vec256`/`Vec128` corollaries
at the end do.

So **do not copy it**. Lift the generic part into `Kopis/Bits/Lanes.lean` — the shared home
`Kopis/Bits/Stream.lean` already establishes for exactly this reason — and leave each backend's
`Lanes.lean` as its own `bits_inj` corollaries. That is a small refactor of the AVX2 stack, so do
it on a green tree and re-run `make prove-kopis` before and after.

### Phase C — `ser::deserialize` is bit-identical to the portable unpacker

```lean
theorem neon_deserialize_eq (bytes : Slice U8) (bits : Usize) (h : …) :
  RustKopisNeon.backend.neon.ser.deserialize bytes bits
    = RustKopisNeon.ser.deserialize_generic bytes bits
```

The closest analogue in the tree, and the cleanest first real target. `Kopis/Avx2/SerPlan.lean`,
`SerLane.lean`, `SerTail.lean`, `Ser.lean` and `SerGeneric.lean` are the template and the
argument is the same one; what differs is the instruction sequence. Per group of 8 coefficients:

| | AVX2 | NEON |
|---|---|---|
| broadcast | `vbroadcasti128` to both halves | not needed — one 128-bit register |
| select bytes | `vpshufb`, index masked to `& 0x0F`, zero on bit 7 | `tbl`, whole register, zero on index ≥ 16 |
| shift | `vpsrlvd`, one pass over 8 lanes | `ushl` × 2, four lanes each, *negated* counts |
| reassemble | `vpackusdw` + `vpermq 0b11_01_10_00` | `xtn`/`xtn2`, already in order |

The tail argument (`⌊15/bits⌋` groups read from a zero-padded 32-byte scratch buffer) is
*identical*, and `head_load_in_bounds` should port with a change of constants only. `PLANS` is
built by the same `const fn` shape, so `PLANS_spec` ports too — note NEON's `shift` table holds
the **negation** of AVX2's, since `ushl` spells a right shift as a negative left shift.

**Acceptance:** proved for all `bits ∈ 1..=13`, no `sorry`.

### Phase D — `sample::cbd_lanes` is bit-identical to the portable sampler

`RustKopisNeon.backend.neon.sample.cbd_lanes MU buf = RustKopisNeon.sample.cbd MU buf out` for
`MU ∈ {6, 10}` — **and only those two.** NEON's `secret` diverts to the portable sampler when
`MU` is a multiple of 8, so `MU = 8` never reaches `cbd_lanes` from the batched path; the
in-loop dispatch in `sample.rs` guards on `!MU.is_multiple_of(8)` too. AVX2's phase D covers
`{6, 8, 10}`. Prove all three anyway if it is free — `cbd_lanes` is total — but the dispatch
proof only needs two.

The popcount step is *simpler* than AVX2's: `cnt.16b` is a real per-byte population count, so
`popcount_small` is one instruction rather than a `vpshufb` nibble lookup plus bit 4. Its side
condition is different too — validity needs each 16-bit lane's **high byte to be zero**, not the
lane to be below 32. Derive it from `MU/2 ≤ 5` as before.

`Kopis/Avx2/CbdGeneric.lean` is 1672 lines of ported portable-side proof; its NEON twin is the
same substitution and should compile first try, as the AVX2 one did.

### Phase E — the twin stack and the eight dispatch theorems

As AVX2's phase E, and cheaper by (a) in §1: `available` is `ok true`, so each dispatch theorem
is one branch rather than two, and there is no bridge script to write. Generalize
`scripts/gen_avx2_twins.py` to take the backend as a parameter rather than copying it; the
`Makefile`'s `audit_copy` is already parameterized that way and is the model.

Then: `lean_lib «KopisNeonProperties»`, `TopLevelTheoremsNeon` into `prove-kopis-neon`, and the
third row in `TrustBase.lean` — with the prose the existing NEON section there asks for, about
the axioms not being silicon-checked if phase A is still open.

### Phase F — the NTT, and the two-way TurboSHAKE

The hard ones. Order them by what transfers:

1. **`mont_mul` / `barrett` lane specs.** NEON's `mont_mul` is *not* AVX2's: it is
   `shsub(sqdmulh(a, z), sqdmulh(t, q))` — two doubled high-multiplies subtracted and halved once
   — against AVX2's `sub(mulhi(a, z), mulhi(t, q))`. The `intrinsics.rs` comment gives the
   argument (both `sqdmulh` results carry the *same* carry bit, because it depends only on the
   shared low half, so `shsub` cancels it exactly). That argument is the theorem; it has no AVX2
   counterpart and is the first genuinely new piece of mathematics in this plan.
2. **`transpose8` is a permutation.** Lane `m` of `v[k]` holds what was lane `k` of `v[m]`, and
   twice is the identity. Three `TRN` stages, no half-boundary subtleties. The Rust test
   `transpose8_permutes_as_documented` states exactly the property.
3. **The growth bound.** See §2(c): this is the crude budget, not AVX2's sharp one, so it should
   be the easier of the two — but it is a different theorem and `NttGrowth.lean` does not port.
4. **The end-to-end CRT theorem**, through the existing `NttMath.lean`, as AVX2's F4.
5. **`keccak::xof2`.** The AVX2 four-way proof (`Kopis/Avx2/Keccak/*`) is the template and the
   spec side transfers in full — same Keccak-p[1600, 12], same round constants, same fused
   round read by destination. What changes is that FEAT_SHA3 does in one instruction what AVX2
   spells in several: `xar` is θ's xor and ρ's rotate, `bcax` is a whole χ lane, `rax1` is θ's
   mixing, `eor3` folds three ways. So the round proof should get *shorter*, and the axioms for
   those four are the ones to have tested hardest in phase A — they are doing the most work per
   axiom of anything in the file.

**Two things worth writing down for whoever picks this up.**

`interval_cases` needs `import Mathlib.Tactic.IntervalCases`, which only `Kopis/Avx2/Crt.lean`
and `Kopis/Avx2/NttAlgebra.lean` pull in — the extraction-facing files do not, and neither does

conclude the tactic is missing, as a first reading of the failure suggests.

following `intro` fails with "no additional binders"; use `rename_i` instead. This cost a
build cycle in `Transpose.lean`.

  Three things learned writing them, each of which cost a build cycle:

  (i) **Write the partner index so it is in range unconditionally.**  `Vec128` has no `Inhabited`
  instance, so every `vAt` carries a bound proof, and a statement like
  `laneZ q (vAt v (j+4) _)` cannot be *stated* — the proof `j + 4 < 8` is only available inside
  the branch where `j < 4`.  Writing the pair as `vAt v (j % 4)` and `vAt v (j % 4 + 4)` fixes
  it: both are in range for every `j < 8`, and they name the right vectors on both sides of the
  pairing.  Same trick at `len = 2` (`4·(j/4) + j%2`, `+2`) and `len = 1` (`2·(j/2)`, `+1`).

  (ii) **`rw [hjq]` where `hjq : j / 4 = h` fails with "motive is not type correct"** whenever
  `j / 4` occurs inside a `vAt` bound proof.  Rewrite the *twiddle index alone* instead — pull out
  `have hpsi : ψ2 i1.val m = ψ2 (2·g + j/4) m := by rw [hi1v, hjq]` and rewrite with that.

  (iii) **A nested `if` postcondition is not an equation.**  In `ntt_len1_val` the recursive
  hypothesis is `if j % 2 = 0 then _ = _ else _ = _`; `rw [hrj]` fails.  Split on the parity
  first, `rw [if_pos hpar] at hrj ⊢`, and only then rewrite.

  **A specification defect, found by starting `Reduce.lean`, and fixed.**

  `GSLevel` was defined as `LevelStep Q Zb (2·B) T ∧ …`, and `LevelStep`'s third conjunct is
  `A + T ≤ 2¹⁵ − 1`.  That is the *Cooley-Tukey* fit condition — `a ± t` must not wrap — and
  Gentleman-Sande does not need it: it computes `a + b` (bounded `2B`) and a Montgomery product
  (bounded `T`), never their sum.  `gs_butterfly_spec` asks only for `2·B ≤ 32767`.

  The over-strictness was not merely wasteful; it hid a wrong assumption.  With `A + T ≤ 32767`
  the inverse chain only closed if it *started* from a centred block, so `invntt_block_bnd_q1` /
  `_q2` were stated with input `3840` / `5376`.  The real input is `reduce_block`'s output, which
  is `B32/2¹⁶ + q/2` rounded up — **`4741` at `q₁` and `7141` at `q₂`** — and with that input the
  second transposed level needs `2B + T = 36284`, which `LevelStep` rejects.  The old theorems

  **F5 is much smaller than the AVX2 yardstick suggested, and the reason is the SHA-3 extension.**

  AVX2 builds θ, ρ, π and χ out of `vpxor`, `vpandn` and shift pairs — 208 operations per round,
  and `Kopis/Avx2/Keccak/Ops.lean` is 449 lines of lane algebra to describe them.  ARMv8.2's
  SHA-3 extension gives all four directly:

      eor3(a,b,c) = a ^ b ^ c          θ's column fold, three at a time
      rax1(a,b)   = a ^ rotl(b, 1)     θ's mixing term, exactly
      xar(a,b,#n) = rotr(a ^ b, n)     θ's per-lane xor *composed with* ρ's rotation
      bcax(a,b,c) = a ^ (b & ~c)       χ, in one instruction

  One NEON round is **65 instructions** (25 `xar`, 25 `bcax`, 10 `eor3`, 5 `rax1`), and each maps
  onto a spec-level operation with no intermediate.  `Kopis/Neon/Keccak/Ops.lean` is **117 lines**
  against AVX2's 449, and `State.lean` **151** against 192.  Expect `RoundSpec` to shrink by a
  similar factor: the 25 per-lane goals are the same, but each is one instruction deep instead of
  eight.  This is also the concrete reason `build.rs` insists on `+sha3`.

  `bcax`'s **third** operand is the complemented one.  χ is `B[x] ^ (~B[x+1] & B[x+2])`, so the
  call is `bcax(B[x], B[x+2], B[x+1])` — the last two swapped relative to the formula's reading
  order.  `chiRow_of` is stated so that getting this wrong cannot typecheck.

  `xar` rotates **right**, so ρ's left rotation by `r` is `xar` with `IMM = (64 − r) % 64` — which
  is what `theta_rho!` computes, and the `% 64` is what keeps ρ's one `r = 0` entry from asking
  for 64.  `rotateRight_compl` is the bridge.

  **`round_spec` is the next piece**, and it is the largest single proof left in F5:

      theorem round_spec (src dst : Std.Array Vec128 25#usize) (rc : Vec128) (iᵣ : ℕ)
          (hrc : ∀ l < 2, lane64 rc l = rcWord iᵣ) :
          backend.neon.keccak.round src dst rc
            ⦃ (r : Std.Array Vec128 25#usize) => ∀ l < 2, ∀ x y : Fin 5,
                stateWords r l x y = RndW (stateWords src l) iᵣ x y ⦄

  `dst` does not appear in the postcondition because all 25 registers are overwritten, which
  `idx_surjective` certifies.  Take `l` and `hl : l < 2` as *parameters* rather than writing
  `∀ l < 2` inside the postcondition — `step*` introduces the binders either way, and with the
  `∀` inside, `rename_i` binds the proof where the index is meant.  After `step*`, collapse the
  26 `Array.update`s with `simp +decide only [getElem!_list_set, …]` (`+decide`, not plain
  `simp only`: the side condition is a bound on the *write* index and plain `simp only` cannot
  discharge it, so the lemma silently never fires), then close each of the 25 per-lane goals by
  folding registers into spec vocabulary with `parity_of`, `dTerm_of`, `tVal_of`, `chiRow_of`,
  ending at `RndW_fused`.  Fold the register side *into* the spec's vocabulary, never the other
  way: expanding the spec into raw xors leaves two large trees differing only by AC, and
  `BitVec.xor_comm`'s term ordering is superlinear in atom size.

  first `xar`.  `xar_step` carries two side hypotheses — `0 ≤ IMM.val` and `IMM.val ≤ 63` — that

        | (apply WP.spec_bind (xar_step _ _ _ (by decide) (by decide)); intro _ _)
        | (apply WP.spec_bind (eor_step _ _); intro _ _)

  1. **Twenty-five hypothesis-free `xar` instances.**  `step` never fires on the generic

     `have hk : iN = a#usize := UScalar.eq_of_val_eq (by rw [iN_post]; decide)`, then **`subst`,
     not `rw`** — rewriting the index breaks the `getElem` bound proof's motive — and the lookup
     collapses by `rfl`.
  3. The folding is then five `parity_of`, five `dTerm_of`, twenty-five `tVal_of` (each closing
     with `rw [t_post i hi, hlk]; congr 1` and `decide` for the rotation amount) and twenty-five
     `chiRow_of`.
  4. The 26 writes collapse with one `simp only [stateWords_apply, r_post, dst25_post … dst1_post,
     Std.Array.set_val_eq, i5_post … i49_post]`, then `fin_cases x <;> fin_cases y <;>
     simp +decide only [idx, getElem!_list_set, List.length_set, hdl]` with
     `hdl : dst.val.length = 25 := dst.property`.  Twenty-four goals close with
     `rw [RndW_fused]; norm_num; exact ho{y}{x} l hl`; the `(0,0)` one needs `v85 = v40` first
     (the ι read), which is the same collapse plus **`reduceIte`** — without it `simp only` leaves
     a nest of `if False … if True` unreduced.

  `permute_spec` (`Permute.lean`) then transferred from AVX2 almost verbatim: the ping-pong
  between `state` and `scratch`, `rounds` as the loop invariant, twelve rounds at spec indices
  12 … 23.

  **Left in F5**: `Absorb` (AVX2 348), `Squeeze` (539), `Conform` (169), `Xof2` (126), and
  `SpecState` (67) + `KPBridge` (93) which can be lifted into `Kopis/Keccak/` once the NEON absorb
  exists.  Then `SampleBridge`, `SecretBridge`, and phase E.

### F5 is done: `xof2` is TurboSHAKE

Five commits finished the NEON Keccak stack.

**`Absorb.lean`.** `xof2_loop0_spec` (words two at a time, one `ld1` per sponge transposed by
`trn1.2d`/`trn2.2d`) and `xof2_loop1_spec` (the odd word `RATE / 8` leaves over, through general
registers).  The bridge for the tail is `read8_le_val`: eight bytes copied out and put back
together by `from_le_bytes` spell exactly `leWord64`.  Two traps:

* `core.num.U64.from_le_bytes` returns a `UScalar` wrapper around a `BitVec.cast`, and `simp`
  cannot see through it — `show (BitVec.fromLEBytes (List.map Std.U8.bv a.val)).getLsbD z = _`
  strips it in one step where every `simp only [Std.UScalar.bv, …]` fails.
* `List.getElem!_map` does not exist; use
  `show (List.map f l)[k]! = f (l[k]!) from by simp_lists`.

**`Squeeze.lean`.** The mirror: `xof2_loop2_loop0_spec` stores sixteen bytes per sponge,
`xof2_loop2_loop1_spec` the clipped tail, `xof2_loop2_spec` the outer permute-and-emit loop.
Three things worth recording:

* **`let*` can silently `sorry` a branch.** `let* ⟨v, hv⟩ ← Std.Array.index_usize_spec (i := word)
  (by scalar_tac)` — named rather than positional arguments — elaborated to a `sorryAx` and
  reported *no error at all* under `severity: "error"`.  The whole `if_pos` branch was dead for
  several rounds while the LSP called the file clean.  **Always grep a real `lake build` for
  ``uses `sorry` `` before believing a proof landed**; the LSP error filter will not show it.
  The fix is the positional form, `Array.index_usize_spec state word (by scalar_tac)`.
* `scalar_tac` blows past `maxRecDepth` once the context carries a loop's whole postcondition
  plus a dozen `[> … <]` step markers.  Restating the arithmetic as plain `ℕ` `have`s and calling
  `omega` fixes it; keep `scalar_tac` for the small side goals `step*` leaves behind.
* A `let (s, back) := (x, y)` left by `simp only [Std.Array.to_slice_mut, lift, bind_tc_ok]` will
  not zeta-reduce (`dsimp only`, `simp only []`, `beta_reduce` all decline).  Use the `@[step]`
  lemma `Std.Array.to_slice_mut_spec` with `let*` instead.

**Shared.** `wordByte`, `sqState`, `squeezeByte` and all of `Conform.lean` are stated over
`Words`, never over registers, so they now live in `Kopis/Keccak/{Squeeze,Conform}.lean`, joined
by `SpecState.lean` and `KPBridge.lean`.  `coordX`/`coordY`/`idx_coord` moved next to `idx` in
`Kopis/Keccak/Bits.lean`.  Each backend supplies only `stateByte_eq_wordByte` — the one lemma that
mentions its register width — plus its own `xofN` assembly.

**`Xof2.lean`.** `pad_block_spec` ports verbatim from AVX2 (`pad_block`'s extracted body is
byte-identical), then `xof2_spec` and `xof2_turboSHAKE`.  Two NEON-only wrinkles: the
`is_multiple_of` assertion that `RATE / 8` is odd (discharged by `rcases hR <;> (rw [hwv, h];
decide)`), and the output plumbing — `to_slice_mut` on the `[[u8; N]; 2]`, `split_at_mut 1`, and
two `index_mut_usize`s — which reassembles to `[o0, o1]`, i.e. `outOf o0 o1 l`.

**One new assumption.** `usize::div_ceil` is a compiler intrinsic whose body charon does not
translate, so aeneas leaves it opaque.  `Usize.div_ceil_spec` in `Kopis/Neon/Keccak/Squeeze.lean`
gives it its meaning, `⌈x / y⌉`; it must go in the NEON trust-base row in phase E.

**Left**: `SampleBridge` (AVX2 553 lines), `SecretBridge` (414), then phase E.

### Phase E, part 1: the twin stack generates and 55 of 57 twins compile

`scripts/gen_neon_twins.py` derives its patch list from `gen_avx2_twins.py` rather than
transcribing it.  Two rules made it work, and both cost a false start:

* **A patch's anchor is serial text and must not be renamed** — only the replacement.  The
  anchors are matched *after* the generator's own four substitutions, so the three that name a
  module (`Kopis.Avx2.Properties`, `RustKopisAvx2`, `ExtractedRustAvx2`) do have to be swapped in
  the anchor; nothing else in one may be.
* **The file body may not be blanket-renamed either.**  The serial sources themselves reference
  `Kopis.Avx2.NttAlg`, `Kopis.Avx2.q1`, `Kopis/Avx2/Crt.lean` — the two-prime algebra lives on the
  AVX2 side and is *shared*, not duplicated — so `Avx2 → Neon` over the body points them at
  modules that do not exist.

The six dispatch patches needed one NEON-only line each: AVX2's `obtain ⟨b, hb⟩ := available_ok`
becomes `obtain ⟨b, hb⟩ : ∃ b, backend.neon.cpu.available = ok b := ⟨true, rfl⟩`.  The case split
is *kept* — both branches are genuinely provable, the `false` one being the serial proof — because
collapsing it would mean deleting the rest of each theorem rather than changing one line.  NEON
therefore carries no `available_ok` in its trust base.

`Kopis/Neon/SampleBridge.lean` and `Kopis/Neon/SecretBridge.lean` are written.  The matrix one is
the AVX2 file at two lanes plus three structural differences (`bufs` threaded through the loop
rather than allocated per iteration; the deserialize loop takes the whole 416-byte buffer instead
of slicing to `MATRIX_ELEM_BYTES`; the lane count is the `@[irreducible]` `keccak::WAYS`, which
needs `unseal` before each theorem).  The secret one is *not* the AVX2 file: NEON batches two rows
per `xof2` call exactly as its matrix sampler does, where AVX2 asserts `L ≤ 4` and covers every row
in one call, and its inner loop carries a second `MU % 8 == 0` guard.

**Left in phase E**, and it is the last thing between here and a green `make prove-kopis`:

1. `Kopis/Neon/Properties/GenSecretTop.lean`.  NEON's `sample::gen_secret_from_seed_loop` takes an
   extra leading `Bool` — aeneas hoisted the compile-time-`true` probe out of the loop — and its
   body has the three-way `MU % 8` / flag guard.  `step*` walks *into* that guard and produces
   three goals: two are the serial proof verbatim (byte-aligned, and flag-clear), the third is
   `cbd_lanes` with an `Array.update` write-back instead of the `index_mut` closure.
   `CbdDispatch.lean`'s `gen_secret_neon_branch_eq` is exactly that third arm, but rewriting with
   it is brittle (the two arms were compiled differently, `match` against `.1`/`.2` projections),
   so the two loop theorems want NEON-specific replacements with the tail factored into one
   `hcomb`, as `SecretBridge.lean` does.
2. Then: `lake build KopisNeonProperties` clean, `TopLevelTheoremsNeon`, and a third `backends`
   row in `TrustBase.lean` — whose audited list is obtained by letting the check fail once and
   reading the reported footprint.  Do not forget `Usize.div_ceil_spec`.

`tests/neon_intrinsics_vectors.jsonl` (7.1 MB) is committed. Every one of the 46 wrappers has
≥ 1000 vectors — the runner throws rather than reports success if any is missing, thin, unknown,
or disagrees — and the counts run 1000–1729 per operation.

**The negative check, in two halves, because the machinery has two failure modes.**

*Corrupting a model alone does not compile.* Flipping `Model.xarV`'s `rotateRight` to
`rotateLeft` fails at `Kopis/Neon/Model.lean:549` — `xar_model` no longer follows from
`xar_spec`. The equivalence theorems are what make the runner a test of the *axioms*; a model
cannot drift away from its axiom silently.

*Corrupting an axiom is caught by the runner.* `satS16` is shared between the axiom and the
model, so weakening its bound from 32767 to 32000 changes what is *assumed* and still compiles —
this is exactly the "an axiom is simply wrong" scenario. The runner rejects it immediately, with
`sqdmulh_s16` mismatches. Neither corruption is committed.

**A wider sweep, run in Python against the recorded vectors** rather than through Lean, to find
out which corruptions this vector set can actually distinguish. Twelve independent
re-implementations of the models — written from the Arm ARM in a different language, which is an
independent check of the Lean models in its own right — agree with silicon on every vector.
Then, corrupted, `caught / total`:

| operation | corruption | caught |
|---|---|---|
| `xar` | rotate left instead of right | 975 / 1009 |
| `bcax` | complement the second operand, not the third | 1648 / 1729 |
| `eor3` | complement the third operand | 1729 / 1729 |
| `rax1` | rotate right instead of left | 1063 / 1081 |
| `tbl1_u8` | mask index `& 0x0F` (x86 `pshufb`) instead of zeroing | 950 / 1081 |
| `tbl1_u8` | zero at index ≥ 8 instead of ≥ 16 | 1001 / 1081 |
| `ushl_u16` | negate the shift count | 1048 / 1081 |
| `trn1_16` | take the odd lanes (`trn2`) instead of the even | 1065 / 1081 |
| `shrn16_pair_s32` | keep the low half instead of the high | 1065 / 1081 |
| `sqdmulh_s16` | saturation bound 32767 → 32766 | **0** / 1081 |
| `sqdmulh_s16` | saturation bound 32767 → 32000 | 37 / 1081 |
| `sqdmulh_s16` | saturation bound 32767 → 30000 | 76 / 1081 |

Three things in that table are worth keeping.

* **The 32766 row is a `0` that is correct**, not a hole. `SQDMULH` saturates only when both
  operands are −2^15, where the product is 32768; both 32767 and 32766 send that to `0x7FFF`, and
  for every value at or below 32766 the two definitions agree by construction. It is a
  genuinely equivalent change. The AVX2 side found the same thing and recorded it; this
  reproduces it.
* **The 32000 row is where NEON does better than AVX2 did.** AVX2's first attempt at this
  corruption *passed*, because uniform 32-bit lanes essentially never approach the saturation
  boundary, and it took a boundary-hugging generator to catch it. NEON's `sqdmulh` generator
  catches it out of the box, so §2(a)'s worry about structured inputs was already answered by
  `intrinsics_vectors.rs`.
* **The first `tbl1_u8` corruption is the one that matters** and it is caught by 950 vectors.
  AArch64 `tbl` zeroes on any index ≥ 16; x86 `vpshufb` masks the index and keys zeroing off
  bit 7. `Kopis/Neon/Intrinsics.lean` warns that the two must not be confused, and the vectors
  now enforce that warning rather than merely stating it.

  (A first attempt at a `tbl1_u8` corruption — threshold 16 → 32 — scored 0, and that is a
  *bad* corruption rather than a finding: `laneOf 8 table j` is already 0 for `j ≥ 16`, so the
  two models are equal. If a future sweep produces a surprising 0, check for this before
  concluding the generator is thin.)

**What this does and does not buy.** Not a proof: a differential test over ~1000 inputs per
operation. What it rules out is the failure mode that matters — an axiom that is simply wrong —
and, as the table shows, it rules out every hand-written variant of that failure that was tried,
usually by a margin of a thousand vectors. `TrustBase.lean`, `Kopis/Neon/Model.lean`,
`SpecTests/Neon/Run.lean`, `Kopis/Neon/Intrinsics.lean`, the `Makefile`, `lakefile.lean` and both
READMEs have been updated; they previously stated the gap as open, and it would be wrong to leave
that standing. (`Kopis/Avx2/Intrinsics.lean` carries the same "nothing below is checked against
silicon" sentence and it has been stale there for as long as `make test-avx2-model` has existed;
fix it next time that file is touched, rather than paying a full AVX2 re-elaboration for a
comment.)

The NEON row of the trust base is no longer the weaker of the two.

**`make prove-kopis` re-verified green on this host** after all of the above: three backends,
2017 / 2021 / 2019 jobs, exit 0, no `sorry` outside the aeneas dependency's four. That build
includes `TrustBase.lean`'s footprint check, so the NEON row's 129 assumptions are still exactly
the audited list — the documentation changed, the trust base did not.

Read the module docs of `intrinsics_vectors.rs` before touching its generators: three operations
(`tbl1_u8`, `ushl_u16`/`ushl_u32`, `sqdmulh_s16`) are *vacuous* on uniformly random input and
have structured generators for that reason.

### Setting this up on a fresh host, and the aeneas revision it needs

The Lean work was done in a Linux container — `extract_rust_to_lean.sh` still points
`CHARON`/`AENEAS` at `/home/dev/aeneas` — so a fresh host has no aeneas checkout and `lake` fails
with "package directory not found: ../../aeneas/backends/lean". Clone aeneas as a sibling of
`kopis-rs` and run `lake exe cache get` before anything else. Re-extraction is *not* needed to
run any of this; only the Lean backend of aeneas is, so charon does not have to be built.

**This tree does not build against aeneas `main`, and there is no pin recording that.** It needs

```
aeneas b59d5188  ("Add support for loops in consts", 2026-07-17)
```

or anything at or before it that still carries the same `Std`. The breaking change is the very
next commit, **`e30579c0` — "Add IScalar shift-left/right specs" (2026-07-20)** — 57 lines that
add `@[step]`-tagged `ShiftLeft_spec` / `ShiftRight_spec`. With those in scope `step*` walks one
step *further* than three of our proofs expect: it consumes the `1#i16 <<< i2` that
`Kopis/Avx2/NttGrowth.lean:1157` then tries to handle by hand, and the following
`rw [hi2e, show (1#i16 <<< (10#i32) : Result I16) = ok 1024#i16 from rfl]` reports "did not find
an occurrence of the pattern `i2`" — because `i2` is gone and the shift's result is already bound.
Against `main` (`daa85d7e`) exactly three modules fail: `Kopis/Avx2/NttGrowth.lean` (that
rewrite, twice), `Kopis/Neon/Keccak/Squeeze.lean` (`scalar_tac`, at 235–238) and
`Kopis/Properties/KeyGenCapstone.lean` (`maxRecDepth`). All three build at `b59d5188`.

Two traps in diagnosing this, both of which cost a build cycle here:

* **Do not pick the revision by its mathlib pin.** `main`'s `backends/lean/lake-manifest.json`
  names *exactly* the mathlib revision `lean/lake-manifest.json` does — `fabf563a` — along with
  every other package rev, so that agreement looks like confirmation and is not. Those pins have
  not moved in months; they discriminate nothing.
* **Do not pick it by the manifest's date either.** `lean/lake-manifest.json` was written
  2026-07-22, which is *after* the breaking commit, so the obvious guess (the last aeneas commit
  on or before that date) is wrong — and it was tried, and it failed identically. The manifest
  records when mathlib was resolved, not when the container cloned aeneas.

The right way to find it is the one that worked: read the error, identify which tactic changed
behaviour, and `git log -S`/`--stat` aeneas for the commit that touched it.

Whoever next touches the Lean side should either pin this properly or fix the three proofs to be
robust against the new `@[step]` lemmas — the latter is the better answer, and is small: each is a
hand-rolled step that aeneas now does itself.
